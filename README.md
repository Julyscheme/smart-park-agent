# 智慧园区工单处理 Agent — Smart Park Ticket Workflow

> 面向产业园区物业运营场景的 AI 工单处理工作流，基于 [Dify](https://dify.ai) 平台搭建：一条 12 节点工作流完成「知识库检索 → 信息提取 → 字段校验 → 工单分类 → 安全检测 → 责任人指派 → 工单生成 → 编号固化」全链路。

## Executive Summary

**问题**：园区报修靠"微信群描述 → 客服人工登记 → 主管派单"，信息缺失靠来回追问，派单凭经验，安全类报修容易被当普通工单延误。

**方案**：用户用一句话描述故障，工作流自动完成：关键信息提取（位置/设备/故障/联系方式）→ 必要字段校验（缺了礼貌追问）→ 设备分类 → 安全关键词检测（安全工单强制高优先级）→ 责任部门智能路由 → 标准工单 JSON 生成 → 工单号与时间戳固化（代码节点保证唯一性与真实时间）。可直连物业工单系统。

**实测亮点**：
- 🔧 规则与 LLM 混合编排：判断交给分支/代码节点，生成交给 LLM，结果可控可复现
- 🛡️ 安全工单（电路焦糊味/燃气味）强制高优先级，"其他类"设备结合故障特征智能路由（如电路→电力维修组）
- 📚 RAG 集成并经实测调优：相似度阈值 0.7 → 0.45（hit-testing 实测 0.494 后修正）
- 🔍 全链路日志与节点级追踪，工单号由代码节点固化（同输入两次运行生成不同 UUID，时间戳真实）

## 技术架构

```
开始(start)
  → 知识库查询(kb_query, RAG, top_k=3, 阈值0.45)
  → 信息提取(extract_info, LLM 结构化输出: 位置/设备/故障/联系方式)
  → 必要字段判断(check_fields, if-else)
      ├─ 缺字段 → 追问话术(ask_missing, code) → 输出追问(end_ask)
      └─ 完整   → 工单分类(classify, LLM, 8类设备)
                 → 安全检测(safety_check, code, 关键词规则)
                 → 责任人指派(assign_dept, LLM, 8类→6部门+故障特征判定规则)
                 → 工单生成(gen_ticket, LLM, 结构化 JSON)
                 → 编号固化(ticket_finalize, code, UUID+真实时间戳)
                 → 输出工单(end_ticket)
```

**核心技术栈**：Dify Workflow (DSL v0.7.0) + 通义 qwen-plus-latest ×4（信息提取/分类/指派/生成，temperature 0.1）+ text-embedding-v3（知识库向量化）+ 规则引擎（code 节点实现安全检测与编号固化）

**设计原则**：LLM 只负责语义理解与生成；一切需要确定性/唯一性/可审计的环节（字段校验、安全规则、工单号、时间戳）用条件分支与代码节点保证。

## 快速复现

### 前提
- Dify 实例（Docker 自部署或 cloud.dify.ai）
- 阿里云百炼 API Key（LLM：qwen-plus-latest；Embedding：text-embedding-v3，新用户有免费额度）

### 5 步搭建

1. **配置模型供应商** → Dify 设置 → 模型供应商 → 通义千问（填 Key，LLM + Embedding 都要配）
2. **创建知识库** → 导入 `03-knowledge-base/` 3 份文档（分段 500 tokens / 重叠 50，高质量索引）
3. **导入 DSL** → 创建工作流应用 → 导入 `09-smart-park-agent-v2.dify.yml` → 在「知识库查询」节点重新绑定你的知识库（dataset_ids 跨实例不通用）
4. **测试验证** → 按上方实测表逐条运行（工作流编辑器「运行」或 Service API）
5. **发布** → 获取运行日志与 API 接入能力

> 详细步骤与排错见 [02-dify-config-guide.md](./02-dify-config-guide.md)，预计耗时 40-60 分钟。
